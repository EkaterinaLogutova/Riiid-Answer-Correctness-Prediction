## `mart_users`

### Назначение

`mart_users` — пользовательская аналитическая витрина для анализа активности, успешности обучения, прогресса и характера взаимодействия студентов с образовательной системой.

Витрина используется для:

* сравнения пользователей по уровню активности;
* анализа успешности обучения;
* оценки прогресса студентов;
* сегментации пользователей по динамике результатов;
* анализа использования лекций и объяснений;
* построения пользовательских срезов в дашборде.

### Гранулярность

**Одна строка = один уникальный пользователь (`user_id`).**

Каждый пользователь представлен в витрине только один раз.

### Источник данных

Основной источник:

```text
data/processed/mart_events.parquet
```

`mart_users` не обращается напрямую к `train.csv`, `questions.csv` или `lectures.csv`. Все необходимые события и признаки уже содержатся в `mart_events`.

Схема построения:

```text
train.csv
questions.csv
lectures.csv
        ↓
   mart_events
        ↓
   mart_users
```

### Ключ

Основной ключ витрины:

| Поле      | Тип     | Описание                          |
| --------- | ------- | --------------------------------- |
| `user_id` | integer | Уникальный идентификатор студента |

Проверка уникальности:

```python
assert users["user_id"].is_unique
```

## Основные поля

### Активность

| Поле               | Смысл                           | Расчёт                                     |
| ------------------ | ------------------------------- | ------------------------------------------ |
| `questions_count`  | Количество решённых вопросов    | Число событий с `content_type_id = 0`      |
| `lectures_count`   | Количество просмотренных лекций | Число событий с `content_type_id = 1`      |
| `events_count`     | Общее количество событий        | Количество всех событий пользователя       |
| `sessions_count`   | Количество учебных сессий       | Число уникальных `session_id`              |
| `unique_questions` | Количество различных вопросов   | `nunique(question_id)`                     |
| `unique_parts`     | Количество различных разделов   | `nunique(part)`                            |
| `unique_tags`      | Количество различных тем        | Количество уникальных тегов из поля `tags` |

`events_count` должно быть не меньше `questions_count`, поскольку вопрос является одним из типов событий:

```python
assert (
    users["events_count"] >= users["questions_count"]
).all()
```

## Успешность обучения

| Поле                  | Смысл                                 | Расчёт                                             |
| --------------------- | ------------------------------------- | -------------------------------------------------- |
| `correct_answers`     | Количество правильных ответов         | Сумма `answered_correctly` по вопросам             |
| `incorrect_answers`   | Количество неправильных ответов       | `questions_count - correct_answers`                |
| `accuracy`            | Общая доля правильных ответов         | `correct_answers / questions_count`                |
| `first_10_accuracy`   | Accuracy первых 10 вопросов           | Среднее `answered_correctly` первых 10 вопросов    |
| `first_20_accuracy`   | Accuracy первых 20 вопросов           | Среднее `answered_correctly` первых 20 вопросов    |
| `last_10_accuracy`    | Accuracy последних 10 вопросов        | Среднее `answered_correctly` последних 10 вопросов |
| `last_20_accuracy`    | Accuracy последних 20 вопросов        | Среднее `answered_correctly` последних 20 вопросов |
| `best_correct_streak` | Максимальная серия правильных ответов | Максимум `correct_streak`                          |
| `max_error_streak`    | Максимальная серия ошибок             | Максимум `error_streak`                            |

Все метрики успешности рассчитываются **только для question events**.

Для лекций `answered_correctly` не используется.

#### Accuracy

Общая accuracy пользователя:

```text
accuracy =
correct_answers / questions_count
```

Значение находится в диапазоне `[0, 1]`.

Например:

```text
80 правильных ответов
100 решённых вопросов

accuracy = 80 / 100 = 0.80
```

или 80%.

Проверка:

```python
assert users["accuracy"].dropna().between(0, 1).all()
```

## Прогресс

Для оценки прогресса сравнивается качество решения первых и последних вопросов пользователя.

Основная метрика:

```text
progress_20 =
last_20_accuracy - first_20_accuracy
```

Например:

```text
first_20_accuracy = 0.55
last_20_accuracy  = 0.70

progress_20 = 0.70 - 0.55 = +0.15
```

Положительное значение означает улучшение результата, отрицательное — ухудшение.

### Минимальная история

Чтобы не считать пользователя прогрессирующим на основании слишком малого количества наблюдений, для расчёта `progress_20` используется минимум:

```text
40 решённых вопросов
```

Если пользователь решил менее 40 вопросов:

```text
progress_20 = NaN
progress_segment = NaN
```

Это позволяет избежать нестабильной классификации пользователей с очень короткой историей.

### Сегментация прогресса

Используются следующие границы:

```text
progress_20 >= +0.05 → progressing

progress_20 <= -0.05 → declining

-0.05 < progress_20 < +0.05 → stable
```

Таким образом:

* `progressing` — заметное улучшение;
* `stable` — существенной динамики нет;
* `declining` — заметное ухудшение.

Границы сегментации являются параметрами аналитического слоя и при необходимости могут быть изменены после анализа распределения `progress_20`.

## Использование образовательных материалов

| Поле                   | Смысл                                         | Расчёт                                   |
| ---------------------- | --------------------------------------------- | ---------------------------------------- |
| `lecture_views`        | Количество просмотренных лекций               | Количество lecture events                |
| `lecture_per_question` | Количество лекционных событий на один вопрос  | `lecture_views / questions_count`        |
| `explanation_rate`     | Доля вопросных событий с признаком объяснения | Среднее `prior_question_had_explanation` |

#### `lecture_per_question`

Метрика показывает интенсивность использования лекционного материала относительно количества решённых вопросов:

```text
lecture_per_question =
lecture_views / questions_count
```

Например, значение `0.5` означает в среднем 0.5 просмотра лекции на один решённый вопрос.

#### `explanation_rate`

В исходной структуре Riiid `prior_question_had_explanation` является историческим признаком и относится к предыдущему набору вопросов.

Поэтому в `mart_users` эта метрика интерпретируется как:

> доля вопросных событий пользователя, для которых исторический признак `prior_question_had_explanation` равен `True`.

Она **не должна интерпретироваться как строгое количество объяснений, просмотренных непосредственно после каждого вопроса**.

## Связь с `mart_events`

`mart_events` содержит историю действий пользователя, поэтому она является базовой витриной для построения `mart_users`.

```text
mart_events
│
├── user_id
├── timestamp
├── content_type_id
├── answered_correctly
├── question_id
├── part
├── tags
├── session_id
├── correct_streak
├── error_streak
├── time_since_last_event
└── ...
        │
        ↓
    GROUP BY user_id
        │
        ↓
mart_users
```

В `mart_users` не пересчитываются сложные последовательностные признаки, которые уже были рассчитаны в `mart_events`. Например, `best_correct_streak` и `max_error_streak` получаются агрегированием существующих `correct_streak` и `error_streak`.

## Data Quality

Для `mart_users` выполняются следующие проверки.

#### 1. Уникальность пользователя

```python
assert users["user_id"].is_unique
```

Одна строка должна соответствовать одному пользователю.

#### 2. Диапазон accuracy

```python
assert users["accuracy"].dropna().between(0, 1).all()
```

Accuracy не может быть меньше 0 или больше 1.

#### 3. Согласованность ответов

```python
assert (
    users["correct_answers"] + users["incorrect_answers"]
    == users["questions_count"]
).all()
```

Количество правильных и неправильных ответов должно совпадать с количеством решённых вопросов.

#### 4. Количество событий

```python
assert (
    users["events_count"] >= users["questions_count"]
).all()
```

Общее количество событий не может быть меньше количества вопросов.

#### 5. Ограничение по истории

```python
assert users.loc[
    users["questions_count"] < 40,
    "progress_20"
].isna().all()
```

Пользователь с недостаточной историей не должен получать значение прогресса.

Аналогично проверяется `progress_segment`.

#### 6. Диапазон прогресса

```python
assert users["progress_20"].dropna().between(-1, 1).all()
```

Разность двух accuracy не может выйти за пределы `[-1, 1]`.

#### 7. Бесконечные значения

После деления не должны появляться `inf` и `-inf`:

```python
assert not np.isinf(
    users.select_dtypes(include=np.number).to_numpy()
).any()
```

* сравнения групп пользователей;
* анализа прогресса;

В отличие от `mart_events`, витрина не сохраняет временную последовательность отдельных действий. Для анализа поведения пользователя во времени используется `mart_events`.

## `mart_questions` — аналитическая витрина вопросов

### Назначение

`mart_questions` — аналитическая витрина уровня отдельного вопроса (`question_id`) для оценки сложности, популярности и потенциальных проблем образовательного контента.

Она используется для анализа:

- самых сложных и самых простых вопросов;
- популярности вопросов;
- вопросов с аномально большим временем ответа;
- различий успешности между новыми и опытными пользователями;
- структуры быстрых и медленных ошибок;
- контекста ошибок пользователя перед вопросом;
- потенциально проблемного образовательного контента.

Основной вопрос витрины:

> Какие вопросы объективно сложны для пользователей, какие требуют необычно много времени и где наблюдаются признаки проблемного контента или различия между стадиями обучения?

---

### Гранулярность и ключ

**Гранулярность:** одна строка = один вопрос.

**Ключ:** `question_id`.

В текущем результате сборки:

- `mart_questions.parquet` — **13 523 строки**;
- **20 полей**;
- суммарно учтено **99 271 300 валидных ответов**;
- **12 171 вопрос** имеет `enough_attempts = TRUE`.

Финальная таблица строится от полного справочника вопросов через `LEFT JOIN`, поэтому логика пайплайна сохраняет вопрос даже при отсутствии событий ответа. В таком случае счётчики становятся равны `0`, а метрики, для которых нужны наблюдения, остаются `NULL`.

В текущем запуске все 13 523 вопроса из справочника встретились в `mart_events`.

---

| Источник | Роль |
|---|---|
| `processed/mart_events.parquet` | История событий пользователей: ответы, `user_id`, `question_id`, `question_number`, `task_container_id`, `answered_correctly`, `prior_question_elapsed_time`, `error_streak` |

## 1. Подготовка времени ответа

### `prior_question_elapsed_time` нельзя использовать напрямую

Мы посмотрели и поняли, что в `mart_events` поле `prior_question_elapsed_time` относится к **предыдущему question bundle**, а не к текущей строке вопроса.

Поэтому прямое агрегирование этого поля по текущему `question_id` давало бы смещённую семантику времени.

В итоге мы перепривязываем время к тому bundle, который пользователь фактически решал.

---

### Проверка консистентности времени внутри bundle

Сначала для каждой пары:чы

```text
user_id × task_container_id
```

проверяется количество различных ненулевых значений `prior_question_elapsed_time`.

Условие качества:

```text
elapsed_variants <= 1
```

В текущем запуске проверено **76 483 597 question bundle**, и bundle с несколькими различными значениями elapsed time не найдено:

```text
inconsistent_bundles = 0
```

---

### Восстановление elapsed time текущего bundle

Для каждого question bundle рассчитываются:

- `bundle_timestamp = MIN(timestamp)`;
- `bundle_first_row_id = MIN(row_id)`;
- `prior_bundle_elapsed_time = MIN(prior_question_elapsed_time)`.

После этого bundle пользователя сортируются по:

```text
bundle_timestamp,
bundle_first_row_id
```

и применяется сдвиг:

```text
elapsed_time = LEAD(prior_bundle_elapsed_time)
```

То есть значение `prior_question_elapsed_time`, записанное в **следующем** bundle, переносится назад к bundle, время которого оно описывает.

#### Следствие

`elapsed_time` — это время **question bundle**, а не индивидуальное время отдельного вопроса внутри bundle.

Если в одном `task_container_id` находится несколько вопросов, всем этим вопросам при расчёте метрик соответствует одно и то же bundle-level время.

Для последнего question bundle пользователя восстановить время таким способом невозможно, поэтому `elapsed_time` остаётся `NULL`.

---

### Распределение времени и пороги быстрых/медленных ответов

Пороги рассчитываются динамически по всем положительным восстановленным значениям `elapsed_time`.

В текущем запуске использовано **75 956 294** наблюдения времени.

| Перцентиль | Значение |
|---:|---:|
| `P25` | `15 017.84 ms` ≈ **15.0 сек** |
| `P50` | `19 693.50 ms` ≈ **19.7 сек** |
| `P75` | `27 187.37 ms` ≈ **27.2 сек** |
| `P95` | `53 159.82 ms` ≈ **53.2 сек** |

Фиксируются два рабочих порога:

```text
FAST_THRESHOLD_MS = P25 = 15 017.84 ms
SLOW_THRESHOLD_MS = P75 = 27 187.37 ms
```

Эти пороги пересчитываются при новой сборке, если изменяется распределение данных.

## 3. Базовый набор событий для метрик

В агрегаты попадают только валидные question events:

```text
content_type_id = 0
question_id IS NOT NULL
answered_correctly IN (0, 1)
```

Lecture events и строки без валидного результата ответа в метрики вопроса не входят.

## 4. Основные метрики

### `attempts`

Количество валидных ответов пользователей на вопрос:

```text
COUNT(*)
```

Метрика отражает число попыток, а не число уникальных пользователей.

---

### `users_count`

Количество уникальных пользователей, отвечавших на вопрос:

```text
COUNT(DISTINCT user_id)
```

Один пользователь может дать несколько ответов на один вопрос, поэтому:

```text
users_count <= attempts
```

---

### `correct_answers`

Количество правильных ответов:

```text
SUM(answered_correctly = 1)
```

---

### `incorrect_answers`

Количество неправильных ответов:

```text
SUM(answered_correctly = 0)
```

Для каждого вопроса выполняется:

```text
correct_answers + incorrect_answers = attempts
```

---

### `accuracy`

Доля правильных ответов:

```text
accuracy = AVG(answered_correctly)
```

что эквивалентно:

```text
accuracy = correct_answers / attempts
```

для вопросов с ненулевым числом ответов.

Диапазон:

```text
0 <= accuracy <= 1
```

Чем выше `accuracy`, тем чаще пользователи отвечают правильно.

---

### `difficulty`

Наблюдаемый показатель сложности вопроса:

```text
difficulty = 1 - accuracy
```

Диапазон:

```text
0 <= difficulty <= 1
```

Интерпретация:

- значение около `0` — вопрос обычно решается правильно;
- значение около `1` — вопрос имеет очень низкую долю правильных ответов.

`difficulty` — это **эмпирическая сложность по поведению пользователей**, а не характеристика вопроса, независимая от аудитории и контекста показа.

---

## 5. Метрики времени ответа

### `median_elapsed_time`

Медиана восстановленного `elapsed_time` для всех валидных ответов на вопрос, где:

```text
elapsed_time > 0
```

В отличие от `mart_topics`, где используется приближённая медиана исходного `prior_question_elapsed_time`, в `mart_questions` используется обычная функция:

```text
MEDIAN(elapsed_time)
```

после предварительного сдвига времени на корректный question bundle.

---

### `mean_elapsed_time`

Среднее восстановленное время:

```text
AVG(elapsed_time)
```

с условием:

```text
elapsed_time > 0
```

---

### Ограничение интерпретации времени

Несмотря на исправленную temporal-привязку, `elapsed_time` остаётся **bundle-level метрикой**.

Поэтому `median_elapsed_time` и `mean_elapsed_time` следует интерпретировать как:

> типичное время bundle, в котором встречался данный вопрос,

а не как точное индивидуальное время решения конкретного `question_id`.

Особенно осторожно следует интерпретировать вопросы из bundle, содержащих несколько вопросов.

---

## 6. Сложность для новых и опытных пользователей

### Границы сегментов

В реализации границы зафиксированы следующим образом:

| Группа | Условие по `question_number` |
|---|---|
| `beginner` | `1–20` |
| промежуточная стадия | `21–100` |
| `experienced` | `101+` |

Вопросы пользователя № 21–100 **не входят ни в `beginner_accuracy`, ни в `experienced_accuracy`**.

---

### `beginner_accuracy`

Accuracy среди ответов, данных пользователем на первых двадцати вопросах его истории:

```text
AVG(answered_correctly)
FILTER (WHERE question_number BETWEEN 1 AND 20)
```

Если вопрос не встречался в beginner-сегменте, значение равно `NULL`.

---

### `experienced_accuracy`

Accuracy среди ответов пользователей начиная со 101-го вопроса:

```text
AVG(answered_correctly)
FILTER (WHERE question_number >= 101)
```

Если вопрос не встречался в experienced-сегменте, значение равно `NULL`.

---

### `accuracy_gap`

Разница между наблюдаемой успешностью опытных и новых пользователей:

```text
accuracy_gap =
    experienced_accuracy
    - beginner_accuracy
```

Интерпретация:

- `accuracy_gap > 0` — опытные пользователи отвечают на вопрос успешнее;
- `accuracy_gap < 0` — beginner-группа имеет более высокую наблюдаемую accuracy;
- значение около `0` — заметной разницы между двумя сегментами нет.

Если одна из двух accuracy отсутствует, `accuracy_gap = NULL`.

---

### Надёжность `accuracy_gap`

В ноутбуке отдельно проверяется достаточность наблюдений для сравнения сегментов.

Используется порог:

```text
MIN_SEGMENT_ATTEMPTS = 30
```

Сравнение считается надёжным только если:

```text
beginner_attempts >= 30
AND experienced_attempts >= 30
```

В текущем запуске среди вопросов с рассчитанным `accuracy_gap`:

- **8 178** сравнений удовлетворяют этому условию;
- **3 878** — не удовлетворяют;
- доля надёжных сравнений — **67.8%**.

#### Важно

Поля:

- `beginner_attempts`;
- `experienced_attempts`;
- `reliable_accuracy_gap`

используются в диагностике ноутбука, но **не сохраняются в `mart_questions.parquet`**.

Поэтому для dashboard-рейтинга по `ABS(accuracy_gap)` одного условия `enough_attempts = TRUE` недостаточно для строгой оценки надёжности сегментного сравнения. Если рейтинг используется для продуктовых выводов, рекомендуется дополнительно применять правило минимум 30 наблюдений в каждой группе.

---

## 7. Надёжность общей оценки сложности

### Анализ распределения `attempts`

Порог не задаётся произвольно. Сначала рассчитывается распределение числа ответов по вопросам.

В текущем запуске:

| Статистика | `attempts` |
|---:|---:|
| минимум | 1 |
| `P01` | 76 |
| `P05` | 153 |
| `P10` | 283 |
| `P25` | 1 764 |
| `P50` | 4 732 |
| `P75` | 8 557 |
| `P90` | 15 950 |
| `P95` | 22 467 |
| `P99` | 45 977 |
| максимум | 213 605 |

---

### `MIN_ATTEMPTS`

Формула выбора порога:

```text
MIN_ATTEMPTS = max(100, P10(attempts))
```

В текущем запуске:

```text
P10 = 283
MIN_ATTEMPTS = 283
```

---

### `enough_attempts`

Флаг рассчитывается как:

```text
enough_attempts = attempts >= 283
```

В текущем файле:

- всего вопросов: **13 523**;
- `enough_attempts = TRUE`: **12 171**;
- ниже порога: **1 352**.

Порог должен пересчитываться при новой сборке, потому что он зависит от распределения `attempts`.

#### Использование

`enough_attempts` обязателен для:

- рейтинга самых сложных вопросов;
- рейтинга самых простых вопросов;
- поиска аномально долгих вопросов;
- продуктовых выводов о сложности вопроса.

Вопросы ниже порога не удаляются из витрины: они просто исключаются из основного рейтинга сложности.

## 8. Дополнительные признаки

### `fast_incorrect_rate`

Доля ответов с **известным положительным временем**, которые одновременно являются:

1. неправильными;
2. быстрыми — `elapsed_time <= P25`.

Формула:

```text
fast_incorrect_rate =
    count(
        answered_correctly = 0
        AND elapsed_time > 0
        AND elapsed_time <= FAST_THRESHOLD_MS
    )
    /
    count(elapsed_time > 0)
```

В текущем запуске:

```text
FAST_THRESHOLD_MS ≈ 15 018 ms
```

#### Важно

Знаменатель — **все ответы с известным временем**, а не только быстрые ответы и не только неправильные ответы.

Поэтому метрика отвечает на вопрос:

> Какая доля всех наблюдаемых по времени ответов на этот вопрос является одновременно быстрой и неправильной?

Высокое значение может быть признаком поспешных ошибок, угадывания или неочевидной формулировки, но само по себе не доказывает конкретную причину.

---

### `slow_incorrect_rate`

Доля ответов с известным положительным временем, которые одновременно являются:

1. неправильными;
2. медленными — `elapsed_time >= P75`.

Формула:

```text
slow_incorrect_rate =
    count(
        answered_correctly = 0
        AND elapsed_time >= SLOW_THRESHOLD_MS
    )
    /
    count(elapsed_time > 0)
```

В текущем запуске:

```text
SLOW_THRESHOLD_MS ≈ 27 187 ms
```

Высокое значение означает, что существенная доля пользователей тратит относительно много времени и всё равно отвечает неправильно. Это может быть полезным сигналом для поиска сложного или потенциально проблемного контента.

---

### `error_streak_before_avg`

Среднее значение `error_streak` пользователя перед ответом на данный вопрос:

```text
AVG(error_streak)
```

Метрика используется как контекст сложности.

Высокое значение может означать, что вопрос часто встречается пользователям уже после серии ошибок, поэтому низкая `accuracy` может быть связана не только с самим вопросом, но и с состоянием пользователя или сложностью предыдущего участка обучения.

Метрика является дополнительным диагностическим признаком и не используется как основная формула `difficulty`.

---

## 9. Рейтинги и использование на дашборде

### Самые сложные вопросы

Основной рейтинг:

```text
WHERE enough_attempts = TRUE
ORDER BY difficulty DESC, attempts DESC
```

Ключевой фильтр:

```text
enough_attempts = TRUE
```

Нельзя строить основной рейтинг сложности по всем вопросам без фильтра достаточности наблюдений.

---

### Самые простые вопросы

```text
WHERE enough_attempts = TRUE
ORDER BY difficulty ASC, attempts DESC
```

---

### Самые популярные вопросы

```text
ORDER BY attempts DESC
```

Для популярности фильтр `enough_attempts` не обязателен, поскольку сама метрика `attempts` и является мерой наблюдаемости вопроса.

---

### Вопросы с аномально большим временем ответа

Сначала среди вопросов с достаточным числом попыток рассчитывается:

```text
P95(median_elapsed_time)
```

В текущем запуске:

```text
P95 median_elapsed_time = 52 750 ms ≈ 52.7 сек
```

Аномально долгими считаются вопросы:

```text
enough_attempts = TRUE
AND median_elapsed_time >= 52 750 ms
```

Порог пересчитывается при каждой сборке и не является постоянной бизнес-константой.

---

### Различия beginner / experienced

Базовый диагностический рейтинг в ноутбуке:

```text
WHERE
    enough_attempts = TRUE
    AND beginner_accuracy IS NOT NULL
    AND experienced_accuracy IS NOT NULL
ORDER BY ABS(accuracy_gap) DESC
```

Для аналитических выводов рекомендуется дополнительно требовать не менее 30 наблюдений в каждой сравниваемой группе.

---

### Потенциально проблемный контент

В ноутбуке кандидаты ранжируются эвристически:

```text
WHERE enough_attempts = TRUE
ORDER BY
    slow_incorrect_rate DESC NULLS LAST,
    difficulty DESC NULLS LAST,
    median_elapsed_time DESC NULLS LAST
```

То есть приоритет получают вопросы, где одновременно наблюдаются:

- высокая доля медленных неправильных ответов;
- высокая общая сложность;
- большое типичное время ответа.

#### Важно

В финальной витрине **нет отдельного `problematic_content_flag`**.

Это именно способ приоритизации кандидатов для ручного или продуктового анализа, а не автоматическое утверждение, что вопрос содержит ошибку или плохой контент.

то есть вопросы с маленькой выборкой не попадают в основной рейтинг.

## 11. Важные ограничения интерпретации

### `difficulty` не является абсолютной сложностью вопроса

Низкая `accuracy` может зависеть не только от содержания вопроса, но и от:

- состава пользователей, которым он показывается;
- стадии обучения;
- предыдущей истории ошибок;
- `part` и тематики;
- положения вопроса в bundle;
- контекста предыдущих заданий.

Поэтому `difficulty` лучше интерпретировать как **наблюдаемую сложность в имеющемся пользовательском трафике**.

---

### `accuracy_gap` не доказывает эффект обучения

Если `experienced_accuracy > beginner_accuracy`, это не означает автоматически, что пользователи научились решать конкретный вопрос именно благодаря платформе.

Возможные альтернативные объяснения:

- до поздней стадии доходят более сильные пользователи;
- меняется состав пользователей;
- один и тот же вопрос может попадаться сегментам в разном контексте;
- объём наблюдений в beginner и experienced группах может сильно различаться.

Поэтому сравнение следует использовать как диагностический сигнал, а не как causal effect обучения.

---

### Время относится к bundle

`median_elapsed_time`, `mean_elapsed_time`, `fast_incorrect_rate` и `slow_incorrect_rate` используют восстановленное время question bundle.

Это значительно корректнее прямого использования `prior_question_elapsed_time`, но всё равно не позволяет измерить точное время конкретного вопроса внутри multi-question bundle.

---

### Дополнительные признаки не заменяют `difficulty`

`fast_incorrect_rate`, `slow_incorrect_rate` и `error_streak_before_avg` предназначены для дополнительной диагностики.

Основная метрика сложности остаётся:

```text
difficulty = 1 - accuracy
```

при условии достаточного числа наблюдений.

## 1. Промежуточная таблица `question_tags`

### Зачем она нужна

В `questions_clean` поле `tags` может содержать несколько тем в одной строке, например:

```text
question_id = 100
tags = "12 35 72"
```

Для тематической аналитики это преобразуется в:

```text
question_id | tag
------------|----
100         | 12
100         | 35
100         | 72
```

Таким образом один вопрос может относиться одновременно к нескольким темам.

### Схема

| Поле | Тип Parquet | Описание |
|---|---|---|
| `question_id` | `INT64` | Идентификатор вопроса |
| `tag` | `INT32` | Идентификатор образовательной темы |

### Логика формирования

1. Берётся `questions_clean.tags`.
2. Строка разбивается по пробелу.
3. Каждый тег преобразуется в отдельную строку.
4. Тег приводится к целому числу.
5. Невалидные значения исключаются.
6. Используется `DISTINCT`, поэтому пара `question_id × tag` уникальна.

В текущем файле находится **30 992** пары `question_id × tag`.

#### Следствие

Так как вопрос может иметь несколько тегов, один и тот же ответ пользователя может участвовать в метриках нескольких тем.

Поэтому:

```text
SUM(mart_topics.attempts)
```

**не обязана совпадать** с общим количеством ответов в `mart_events`.

## 3. Описание полей и метрик

### `tag`

Идентификатор образовательной темы.

Финальная витрина содержит объединение:

- тегов, встречающихся у вопросов;
- тегов, встречающихся у лекций.

---

### `questions_count`

Количество **уникальных вопросов из справочника** `questions_clean`, которым назначен данный тег.

Формула:

```text
COUNT(DISTINCT question_id)
```

Метрика считается по каталогу вопросов, а не только по вопросам, которые фактически встретились в истории ответов.

---

### `attempts`

Количество валидных ответов пользователей на вопросы данной темы.

Учитываются только question events:

```text
content_type_id = 0
answered_correctly IN (0, 1)
```

Если вопрос содержит несколько тегов, ответ учитывается по каждому из них.

---

### `students_count`

Количество уникальных пользователей, отвечавших на вопросы данной темы:

```text
COUNT(DISTINCT user_id)
```

Сборка `mart_topics` выполняется по user-partition. Все события одного пользователя находятся в одной partition, поэтому последующее суммирование `students_count` между partition не приводит к повторному учёту одного пользователя.

---

### `correct_answers`

Количество правильных ответов:

```text
answered_correctly = 1
```

---

### `incorrect_answers`

Количество неправильных ответов:

```text
answered_correctly = 0
```

Для каждой темы выполняется:

```text
correct_answers + incorrect_answers = attempts
```

---

### `accuracy`

Доля правильных ответов по теме:

```text
accuracy = correct_answers / attempts
```

Рассчитывается только при `attempts > 0`.

Диапазон:

```text
0 <= accuracy <= 1
```

---

### `difficulty`

Показатель сложности темы:

```text
difficulty = 1 - accuracy
```

Чем выше `difficulty`, тем ниже доля правильных ответов и тем сложнее тема по наблюдаемым данным.

Диапазон:

```text
0 <= difficulty <= 1
```

---

### `median_elapsed_time`

Медианное значение `prior_question_elapsed_time` для ответов, связанных с данным тегом.

В сборке по умолчанию используется приближённая медиана:

```text
approx_quantile(prior_question_elapsed_time, 0.5)
```

Это сделано для снижения стоимости вычислений на большом event log.

#### Ограничение интерпретации

В исходном Riiid поле `prior_question_elapsed_time` относится к времени ответа на **предыдущий question bundle**, а не является точным временем решения текущего вопроса.

Поэтому `median_elapsed_time` следует трактовать как **proxy временного поведения**, а не как точное медианное время решения вопросов текущего `tag`.

Для более строгой семантики поле в будущем можно переименовать в:

```text
median_prior_question_elapsed_time
```

---

### `lectures_count`

Количество уникальных лекций в `lectures_clean`, относящихся к теме:

```text
COUNT(DISTINCT lecture_id)
```

Это характеристика объёма доступного лекционного контента, а не количества его просмотров.

---

### `lecture_views`

Общее количество lecture events по данному `tag`.

Каждый просмотр лекции в `mart_events` учитывается как отдельное событие.

Метрика не является количеством уникальных пользователей и не является количеством уникальных лекций.

---

## 4. Связь ответа с предыдущей тематической лекцией

Для каждого ответа определяется, существует ли у этого же пользователя **более ранний** просмотр лекции с тем же `tag`.

Используется temporal `ASOF LEFT JOIN` по:

```text
user_id
tag
question_timestamp > lecture_timestamp
```

То есть лекция считается просмотренной до ответа только если:

1. её просмотрел тот же пользователь;
2. у лекции тот же `tag`;
3. `lecture_timestamp` строго меньше `question_timestamp`.

Если предыдущих подходящих лекций несколько, используется ближайшая предыдущая лекция.

#### Замечание

В текущей логике отсутствует ограничение по давности лекции.

Например, если пользователь посмотрел лекцию по теме, а затем через большой промежуток времени снова отвечает на вопрос этой темы, такой ответ всё равно относится к группе `after_lecture`.

---

### `attempts_after_lecture`

Количество ответов, для которых найдена хотя бы одна более ранняя тематическая лекция.

---

### `accuracy_after_lecture`

Доля правильных ответов среди ответов после предыдущей лекции того же `tag`:

```text
accuracy_after_lecture =
    correct_after_lecture / attempts_after_lecture
```

Рассчитывается только при наличии таких ответов.

---

### `attempts_without_lecture`

Количество ответов, перед которыми в истории пользователя не найдено более ранней лекции того же `tag`.

---

### `accuracy_without_lecture`

Доля правильных ответов в группе без найденной предыдущей тематической лекции:

```text
accuracy_without_lecture =
    correct_without_lecture / attempts_without_lecture
```

---

### `accuracy_difference`

Разница между двумя наблюдаемыми accuracy:

```text
accuracy_difference =
    accuracy_after_lecture
    - accuracy_without_lecture
```

Интерпретация:

- `> 0` — ответы после тематической лекции имеют более высокую наблюдаемую accuracy;
- `< 0` — ответы после тематической лекции имеют более низкую наблюдаемую accuracy;
- около `0` — заметной разницы в агрегированных данных нет.

#### Нельзя интерпретировать как causal effect

Корректно:

> «После предварительного просмотра тематической лекции наблюдается другая accuracy».

Некорректно:

> «Лекция повышает accuracy на X п.п.».

Причины возможного selection bias:

- более мотивированные пользователи чаще смотрят лекции;
- слабые пользователи могут обращаться к лекциям именно после проблем;
- сложность вопросов внутри темы неодинакова;
- пользователи находятся на разных стадиях обучения;
- могут различаться состав тем и история предыдущих действий.

Для причинного вывода требуется отдельный эксперимент / A/B-тест.

---

## 5. Флаги надёжности

### `enough_attempts`

Флаг достаточного количества наблюдений для общего анализа темы.

Текущий порог:

```text
attempts >= 1000
```

Рекомендуется использовать этот флаг при:

- рейтинге самых сложных тем;
- сравнении тем на dashboard;
- формулировке устойчивых продуктовых выводов.

---

### `enough_lecture_comparison`

Флаг достаточной выборки для сравнения групп с лекцией и без неё.

Текущая логика:

```text
attempts_after_lecture >= 500
AND
attempts_without_lecture >= 500
```

Для анализа `accuracy_difference` рекомендуется использовать только строки, где:

```text
enough_lecture_comparison = TRUE
```

---

## 6. `content_gap_flag`

Флаг предназначен для поиска тем, которые одновременно:

1. популярны;
2. имеют низкую успешность;
3. слабо обеспечены лекционным контентом.

Пороги не задаются вручную, а рассчитываются по распределению тем при каждой сборке.

#### High attempts

```text
75-й перцентиль attempts
```

Тема должна удовлетворять:

```text
attempts >= high_attempts_threshold
```

#### Low accuracy

```text
25-й перцентиль accuracy
```

Тема должна удовлетворять:

```text
accuracy <= low_accuracy_threshold
```

#### Low lectures

```text
25-й перцентиль lectures_count
```

Тема должна удовлетворять:

```text
lectures_count <= low_lectures_threshold
```

Итог:

```text
content_gap_flag =
    high attempts
    AND low accuracy
    AND low lectures
```

Флаг предназначен для **приоритизации кандидатов для дальнейшего анализа**, а не для автоматического утверждения, что теме обязательно не хватает контента.

## 7. Data Quality

В пайплайн встроены проверки до сохранения финального `mart_topics.parquet`.

### Уникальность ключа

Проверяется:

```text
COUNT(*) = COUNT(DISTINCT tag)
```

То есть в финальной таблице должна быть ровно одна строка на `tag`.

---

### Корректность accuracy

Для ненулевых значений:

```text
0 <= accuracy <= 1
```

---

### Корректность difficulty

Проверяется:

```text
0 <= difficulty <= 1
```

и

```text
difficulty = 1 - accuracy
```

с учётом допустимой погрешности вычислений с плавающей точкой.

---

### Баланс ответов

Проверяется:

```text
correct_answers + incorrect_answers = attempts
```

---

### Разбиение по наличию лекции

Каждый ответ должен попасть ровно в одну из двух групп:

```text
attempts_after_lecture + attempts_without_lecture = attempts
```

---

### Неотрицательность счётчиков

Проверяется отсутствие отрицательных значений в:

- `questions_count`;
- `attempts`;
- `students_count`;
- `correct_answers`;
- `incorrect_answers`;
- `lectures_count`;
- `lecture_views`.

---

### Уникальность справочника лекций

Проверяется уникальность:

```text
lecture_id
```

в `lectures_clean`.

Это защищает join от размножения lecture events.

---

### Temporal leakage

Для найденной предыдущей тематической лекции обязательно:

```text
lecture_timestamp < question_timestamp
```

Основная логика использует строгое условие:

```text
question_timestamp > lecture_timestamp
```

Дополнительно temporal-check повторяется на одной полной user-partition.

Таким образом будущая лекция не может использоваться как признак для более раннего ответа.

---

## 8. Особенности производительности

Полный `mart_events` содержит очень большой объём событий, поэтому сборка тематической витрины не выполняет один глобальный тяжёлый temporal join.

Используется схема:

```text
mart_events
   ↓
hash(user_id) % 32
   ↓
32 user-partitions
   ↓
question × tag + lecture matching
   ↓
partial metrics
   ↓
aggregation by tag
   ↓
mart_topics
```

Все события одного пользователя всегда находятся в одной partition. Это позволяет корректно рассчитывать историю пользователя независимо внутри каждой части.

Поддерживается `RESUME = True`: уже рассчитанные partial-файлы можно не пересчитывать после прерванного запуска.

## `mart_student_stage`

### Назначение

`mart_student_stage` — агрегированная витрина для анализа того, как меняется поведение и успешность студентов по мере использования платформы.

Основной вопрос витрины:

> Как меняются accuracy, скорость решения и использование образовательных материалов по мере продвижения пользователя?

Источник — `mart_events.parquet`.

---

### Гранулярность

В витрине есть два уровня агрегации:

- `aggregation_level = stage` — одна строка = один этап обучения;
- `aggregation_level = stage_part` — одна строка = один этап обучения × `part`.

Для общих графиков используйте `stage`.  
Для сравнения разделов — `stage_part`.

> У строк `aggregation_level = stage` поле `part` равно `NA` — это нормально.

---

### Этапы обучения

Этап определяется по порядковому номеру вопроса конкретного пользователя:

| `stage_order` | `stage` | Номера вопросов |
|---:|---|---|
| 1 | `1–10` | 1–10 |
| 2 | `11–20` | 11–20 |
| 3 | `21–50` | 21–50 |
| 4 | `51–100` | 51–100 |
| 5 | `101–200` | 101–200 |
| 6 | `201–500` | 201–500 |
| 7 | `501+` | 501 и далее |

`stage_order` нужно использовать для сортировки этапов в дашборде.

У этапа `501+` поле `stage_max_question` равно `NA`, потому что верхней границы нет.

Для лекций этап определяется по текущему прогрессу пользователя: `questions_before + 1`.

---

### Основные поля

| Поле | Что означает |
|---|---|
| `students_count` | число уникальных студентов на этапе |
| `answers_count` | число ответов на вопросы |
| `accuracy` | доля правильных ответов |
| `median_elapsed_time` | медианное время ответа |
| `mean_elapsed_time` | среднее время ответа |
| `lectures_count` | количество просмотров лекций |
| `lecture_rate` | доля студентов этапа, посмотревших хотя бы одну лекцию |
| `explanation_rate` | доля ответов, перед которыми было доступно объяснение |
| `median_error_streak` | медианная длина серии ошибок перед вопросом |
| `avg_questions_per_session` | среднее количество вопросов в сессии |
| `small_sample_flag` | признак маленькой выборки |

`median_elapsed_time` и `mean_elapsed_time` основаны на `prior_question_elapsed_time`.

---

### Что строить на дашборде

Основные графики:

1. `accuracy` по `stage`;
2. `median_elapsed_time` по `stage`;
3. `lecture_rate` по `stage`;
4. `explanation_rate` по `stage`;
5. `accuracy` по `stage` в разрезе `part`.

Для первых четырёх графиков фильтр:

`aggregation_level = stage`

Для графика по разделам:

`aggregation_level = stage_part`

Ось этапов сортировать по `stage_order`, а не по текстовому значению `stage`.

---

### Работа с маленькими выборками

Строка получает:

`small_sample_flag = True`

если `students_count < 100`.

Такие значения не удаляются, но выводы по ним нужно делать осторожно. Особенно это важно для поздних этапов и разреза `stage × part`.

---

### Важное ограничение интерпретации

Рост `accuracy` на поздних этапах **не доказывает эффект обучения сам по себе**.

Причинами также могут быть:

- уход менее успешных пользователей;
- изменение сложности вопросов;
- изменение набора тем и `part`;
- изменение состава студентов, дошедших до поздних этапов.

Поэтому динамику из этой витрины нужно сопоставлять с `mart_questions` и `mart_topics`.

---

Файл:

`data/processed/mart_student_stage.parquet`

Витрина предназначена прежде всего для графиков жизненного цикла пользователя и сравнений этапов обучения.
