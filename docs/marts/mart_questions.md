# `mart_questions` — аналитическая витрина вопросов

## Назначение

`mart_questions` — аналитическая витрина уровня отдельного вопроса (`question_id`) для оценки сложности, популярности и потенциальных проблем образовательного контента.

Она используется для анализа:

- самых сложных и самых простых вопросов;
- популярности вопросов;
- вопросов с аномально большим временем ответа;
- различий успешности между новыми и опытными пользователями;
- структуры быстрых и медленных ошибок;
- контекста ошибок пользователя перед вопросом;
- потенциально проблемного образовательного контента.

Основной вопрос витрины:

> Какие вопросы объективно сложны для пользователей, какие требуют необычно много времени и где наблюдаются признаки проблемного контента или различия между стадиями обучения?

---

## Гранулярность и ключ

**Гранулярность:** одна строка = один вопрос.

**Ключ:** `question_id`.

В текущем результате сборки:

- `mart_questions.parquet` — **13 523 строки**;
- **20 полей**;
- суммарно учтено **99 271 300 валидных ответов**;
- **12 171 вопрос** имеет `enough_attempts = TRUE`.

Финальная таблица строится от полного справочника вопросов через `LEFT JOIN`, поэтому логика пайплайна сохраняет вопрос даже при отсутствии событий ответа. В таком случае счётчики становятся равны `0`, а метрики, для которых нужны наблюдения, остаются `NULL`.

В текущем запуске все 13 523 вопроса из справочника встретились в `mart_events`.

---

## Источники

| Источник | Роль |
|---|---|
| `processed/mart_events.parquet` | История событий пользователей: ответы, `user_id`, `question_id`, `question_number`, `task_container_id`, `answered_correctly`, `prior_question_elapsed_time`, `error_streak` |
| `processed/questions_clean.parquet` | Справочник вопросов: `question_id`, `bundle_id`, `part`, `tags`, `correct_answer` |

Финальный результат:

`processed/mart_questions.parquet`

```text
mart_events.parquet
      │

      │             │
```

# 1. Подготовка времени ответа

## `prior_question_elapsed_time` нельзя использовать напрямую

Мы посмотрели и поняли, что в `mart_events` поле `prior_question_elapsed_time` относится к **предыдущему question bundle**, а не к текущей строке вопроса.

Поэтому прямое агрегирование этого поля по текущему `question_id` давало бы смещённую семантику времени.

В итоге мы перепривязываем время к тому bundle, который пользователь фактически решал.

---

## Проверка консистентности времени внутри bundle

Сначала для каждой пары:чы

```text
user_id × task_container_id
```

проверяется количество различных ненулевых значений `prior_question_elapsed_time`.

Условие качества:

```text
elapsed_variants <= 1
```

В текущем запуске проверено **76 483 597 question bundle**, и bundle с несколькими различными значениями elapsed time не найдено:

```text
inconsistent_bundles = 0
```

---

## Восстановление elapsed time текущего bundle

Для каждого question bundle рассчитываются:

- `bundle_timestamp = MIN(timestamp)`;
- `bundle_first_row_id = MIN(row_id)`;
- `prior_bundle_elapsed_time = MIN(prior_question_elapsed_time)`.

После этого bundle пользователя сортируются по:

```text
bundle_timestamp,
bundle_first_row_id
```

и применяется сдвиг:

```text
elapsed_time = LEAD(prior_bundle_elapsed_time)
```

То есть значение `prior_question_elapsed_time`, записанное в **следующем** bundle, переносится назад к bundle, время которого оно описывает.

### Следствие

`elapsed_time` — это время **question bundle**, а не индивидуальное время отдельного вопроса внутри bundle.

Если в одном `task_container_id` находится несколько вопросов, всем этим вопросам при расчёте метрик соответствует одно и то же bundle-level время.

Для последнего question bundle пользователя восстановить время таким способом невозможно, поэтому `elapsed_time` остаётся `NULL`.

---

## Распределение времени и пороги быстрых/медленных ответов

Пороги рассчитываются динамически по всем положительным восстановленным значениям `elapsed_time`.

В текущем запуске использовано **75 956 294** наблюдения времени.

| Перцентиль | Значение |
|---:|---:|
| `P25` | `15 017.84 ms` ≈ **15.0 сек** |
| `P50` | `19 693.50 ms` ≈ **19.7 сек** |
| `P75` | `27 187.37 ms` ≈ **27.2 сек** |
| `P95` | `53 159.82 ms` ≈ **53.2 сек** |

Фиксируются два рабочих порога:

```text
FAST_THRESHOLD_MS = P25 = 15 017.84 ms
SLOW_THRESHOLD_MS = P75 = 27 187.37 ms
```

Эти пороги пересчитываются при новой сборке, если изменяется распределение данных.

# 3. Базовый набор событий для метрик

В агрегаты попадают только валидные question events:

```text
content_type_id = 0
question_id IS NOT NULL
answered_correctly IN (0, 1)
```

Lecture events и строки без валидного результата ответа в метрики вопроса не входят.

---

# 4. Основные метрики

## `attempts`

Количество валидных ответов пользователей на вопрос:

```text
COUNT(*)
```

Метрика отражает число попыток, а не число уникальных пользователей.

---

## `users_count`

Количество уникальных пользователей, отвечавших на вопрос:

```text
COUNT(DISTINCT user_id)
```

Один пользователь может дать несколько ответов на один вопрос, поэтому:

```text
users_count <= attempts
```

---

## `correct_answers`

Количество правильных ответов:

```text
SUM(answered_correctly = 1)
```

---

## `incorrect_answers`

Количество неправильных ответов:

```text
SUM(answered_correctly = 0)
```

Для каждого вопроса выполняется:

```text
correct_answers + incorrect_answers = attempts
```

---

## `accuracy`

Доля правильных ответов:

```text
accuracy = AVG(answered_correctly)
```

что эквивалентно:

```text
accuracy = correct_answers / attempts
```

для вопросов с ненулевым числом ответов.

Диапазон:

```text
0 <= accuracy <= 1
```

Чем выше `accuracy`, тем чаще пользователи отвечают правильно.

---

## `difficulty`

Наблюдаемый показатель сложности вопроса:

```text
difficulty = 1 - accuracy
```

Диапазон:

```text
0 <= difficulty <= 1
```

Интерпретация:

- значение около `0` — вопрос обычно решается правильно;
- значение около `1` — вопрос имеет очень низкую долю правильных ответов.

`difficulty` — это **эмпирическая сложность по поведению пользователей**, а не характеристика вопроса, независимая от аудитории и контекста показа.

---

# 5. Метрики времени ответа

## `median_elapsed_time`

Медиана восстановленного `elapsed_time` для всех валидных ответов на вопрос, где:

```text
elapsed_time > 0
```

В отличие от `mart_topics`, где используется приближённая медиана исходного `prior_question_elapsed_time`, в `mart_questions` используется обычная функция:

```text
MEDIAN(elapsed_time)
```

после предварительного сдвига времени на корректный question bundle.

---

## `mean_elapsed_time`

Среднее восстановленное время:

```text
AVG(elapsed_time)
```

с условием:

```text
elapsed_time > 0
```

---

## Ограничение интерпретации времени

Несмотря на исправленную temporal-привязку, `elapsed_time` остаётся **bundle-level метрикой**.

Поэтому `median_elapsed_time` и `mean_elapsed_time` следует интерпретировать как:

> типичное время bundle, в котором встречался данный вопрос,

а не как точное индивидуальное время решения конкретного `question_id`.

Особенно осторожно следует интерпретировать вопросы из bundle, содержащих несколько вопросов.

---

# 6. Сложность для новых и опытных пользователей

## Границы сегментов

В реализации границы зафиксированы следующим образом:

| Группа | Условие по `question_number` |
|---|---|
| `beginner` | `1–20` |
| промежуточная стадия | `21–100` |
| `experienced` | `101+` |

Вопросы пользователя № 21–100 **не входят ни в `beginner_accuracy`, ни в `experienced_accuracy`**.

---

## `beginner_accuracy`

Accuracy среди ответов, данных пользователем на первых двадцати вопросах его истории:

```text
AVG(answered_correctly)
FILTER (WHERE question_number BETWEEN 1 AND 20)
```

Если вопрос не встречался в beginner-сегменте, значение равно `NULL`.

---

## `experienced_accuracy`

Accuracy среди ответов пользователей начиная со 101-го вопроса:

```text
AVG(answered_correctly)
FILTER (WHERE question_number >= 101)
```

Если вопрос не встречался в experienced-сегменте, значение равно `NULL`.

---

## `accuracy_gap`

Разница между наблюдаемой успешностью опытных и новых пользователей:

```text
accuracy_gap =
    experienced_accuracy
    - beginner_accuracy
```

Интерпретация:

- `accuracy_gap > 0` — опытные пользователи отвечают на вопрос успешнее;
- `accuracy_gap < 0` — beginner-группа имеет более высокую наблюдаемую accuracy;
- значение около `0` — заметной разницы между двумя сегментами нет.

Если одна из двух accuracy отсутствует, `accuracy_gap = NULL`.

---

## Надёжность `accuracy_gap`

В ноутбуке отдельно проверяется достаточность наблюдений для сравнения сегментов.

Используется порог:

```text
MIN_SEGMENT_ATTEMPTS = 30
```

Сравнение считается надёжным только если:

```text
beginner_attempts >= 30
AND experienced_attempts >= 30
```

В текущем запуске среди вопросов с рассчитанным `accuracy_gap`:

- **8 178** сравнений удовлетворяют этому условию;
- **3 878** — не удовлетворяют;
- доля надёжных сравнений — **67.8%**.

### Важно

Поля:

- `beginner_attempts`;
- `experienced_attempts`;
- `reliable_accuracy_gap`

используются в диагностике ноутбука, но **не сохраняются в `mart_questions.parquet`**.

Поэтому для dashboard-рейтинга по `ABS(accuracy_gap)` одного условия `enough_attempts = TRUE` недостаточно для строгой оценки надёжности сегментного сравнения. Если рейтинг используется для продуктовых выводов, рекомендуется дополнительно применять правило минимум 30 наблюдений в каждой группе.

## `MIN_ATTEMPTS`

Формула выбора порога:

```text
MIN_ATTEMPTS = max(100, P10(attempts))
```

В текущем запуске:

```text
P10 = 283
MIN_ATTEMPTS = 283
```

---

## `enough_attempts`

Флаг рассчитывается как:

```text
enough_attempts = attempts >= 283
```

В текущем файле:

- всего вопросов: **13 523**;
- `enough_attempts = TRUE`: **12 171**;
- ниже порога: **1 352**.

Порог должен пересчитываться при новой сборке, потому что он зависит от распределения `attempts`.

### Использование

`enough_attempts` обязателен для:

- рейтинга самых сложных вопросов;
- рейтинга самых простых вопросов;
- поиска аномально долгих вопросов;
- продуктовых выводов о сложности вопроса.

Вопросы ниже порога не удаляются из витрины: они просто исключаются из основного рейтинга сложности.

# 8. Дополнительные признаки

## `fast_incorrect_rate`

Доля ответов с **известным положительным временем**, которые одновременно являются:

1. неправильными;
2. быстрыми — `elapsed_time <= P25`.

Формула:

```text
fast_incorrect_rate =
    count(
        answered_correctly = 0
        AND elapsed_time > 0
        AND elapsed_time <= FAST_THRESHOLD_MS
    )
    /
    count(elapsed_time > 0)
```

В текущем запуске:

```text
FAST_THRESHOLD_MS ≈ 15 018 ms
```

### Важно

Знаменатель — **все ответы с известным временем**, а не только быстрые ответы и не только неправильные ответы.

Поэтому метрика отвечает на вопрос:

> Какая доля всех наблюдаемых по времени ответов на этот вопрос является одновременно быстрой и неправильной?

Высокое значение может быть признаком поспешных ошибок, угадывания или неочевидной формулировки, но само по себе не доказывает конкретную причину.

---

## `slow_incorrect_rate`

Доля ответов с известным положительным временем, которые одновременно являются:

1. неправильными;
2. медленными — `elapsed_time >= P75`.

Формула:

```text
slow_incorrect_rate =
    count(
        answered_correctly = 0
        AND elapsed_time >= SLOW_THRESHOLD_MS
    )
    /
    count(elapsed_time > 0)
```

В текущем запуске:

```text
SLOW_THRESHOLD_MS ≈ 27 187 ms
```

Высокое значение означает, что существенная доля пользователей тратит относительно много времени и всё равно отвечает неправильно. Это может быть полезным сигналом для поиска сложного или потенциально проблемного контента.

---

## `error_streak_before_avg`

Среднее значение `error_streak` пользователя перед ответом на данный вопрос:

```text
AVG(error_streak)
```

Метрика используется как контекст сложности.

Высокое значение может означать, что вопрос часто встречается пользователям уже после серии ошибок, поэтому низкая `accuracy` может быть связана не только с самим вопросом, но и с состоянием пользователя или сложностью предыдущего участка обучения.

Метрика является дополнительным диагностическим признаком и не используется как основная формула `difficulty`.

---

# 9. Рейтинги и использование на дашборде

## Самые сложные вопросы

Основной рейтинг:

```text
WHERE enough_attempts = TRUE
ORDER BY difficulty DESC, attempts DESC
```

Ключевой фильтр:

```text
enough_attempts = TRUE
```

Нельзя строить основной рейтинг сложности по всем вопросам без фильтра достаточности наблюдений.

---

## Самые простые вопросы

```text
WHERE enough_attempts = TRUE
ORDER BY difficulty ASC, attempts DESC
```

---

## Самые популярные вопросы

```text
ORDER BY attempts DESC
```

Для популярности фильтр `enough_attempts` не обязателен, поскольку сама метрика `attempts` и является мерой наблюдаемости вопроса.

---

## Вопросы с аномально большим временем ответа

Сначала среди вопросов с достаточным числом попыток рассчитывается:

```text
P95(median_elapsed_time)
```

В текущем запуске:

```text
P95 median_elapsed_time = 52 750 ms ≈ 52.7 сек
```

Аномально долгими считаются вопросы:

```text
enough_attempts = TRUE
AND median_elapsed_time >= 52 750 ms
```

Порог пересчитывается при каждой сборке и не является постоянной бизнес-константой.

---

## Различия beginner / experienced

Базовый диагностический рейтинг в ноутбуке:

```text
WHERE
    enough_attempts = TRUE
    AND beginner_accuracy IS NOT NULL
    AND experienced_accuracy IS NOT NULL
ORDER BY ABS(accuracy_gap) DESC
```

Для аналитических выводов рекомендуется дополнительно требовать не менее 30 наблюдений в каждой сравниваемой группе.

---

## Потенциально проблемный контент

В ноутбуке кандидаты ранжируются эвристически:

```text
WHERE enough_attempts = TRUE
ORDER BY
    slow_incorrect_rate DESC NULLS LAST,
    difficulty DESC NULLS LAST,
    median_elapsed_time DESC NULLS LAST
```

То есть приоритет получают вопросы, где одновременно наблюдаются:

- высокая доля медленных неправильных ответов;
- высокая общая сложность;
- большое типичное время ответа.

### Важно

В финальной витрине **нет отдельного `problematic_content_flag`**.

Это именно способ приоритизации кандидатов для ручного или продуктового анализа, а не автоматическое утверждение, что вопрос содержит ошибку или плохой контент.

# 10. Data Quality

В пайплайн встроены проверки до и после сохранения `mart_questions.parquet`.

## Уникальность ключа

Проверяется:

```text
COUNT(*) = COUNT(DISTINCT question_id)
```

В текущем файле:

```text
13 523 rows = 13 523 unique question_id
```

То есть одна строка действительно соответствует одному вопросу.

---

## JOIN со справочником не создаёт дубликаты

Дополнительно проверяется:

```text
COUNT(mart_questions) = COUNT(questions_clean)
```

Это защищает финальную витрину от размножения вопросов после join.

---

## Корректность `accuracy`

Для ненулевых значений:

```text
0 <= accuracy <= 1
```

---

## Корректность `difficulty`

Проверяется:

```text
difficulty = 1 - accuracy
```

с допустимой погрешностью вычислений с плавающей точкой:

```text
ABS(difficulty - (1 - accuracy)) <= 1e-12
```

---

## Баланс ответов

Проверяется:

```text
correct_answers + incorrect_answers = attempts
```

---

## Корректность `enough_attempts`

Проверяется точное соответствие:

```text
enough_attempts = (attempts >= MIN_ATTEMPTS)
```

---

## Диапазон сегментных accuracy

Для ненулевых значений:

```text
0 <= beginner_accuracy <= 1
0 <= experienced_accuracy <= 1
```

---

## Корректность `accuracy_gap`

Проверяется:

```text
accuracy_gap =
    experienced_accuracy
    - beginner_accuracy
```

с погрешностью не более `1e-12`.

---

## Диапазон дополнительных rate-метрик

Для ненулевых значений:

```text
0 <= fast_incorrect_rate <= 1
0 <= slow_incorrect_rate <= 1
```

---

## Проверка основного рейтинга сложности

Отдельно проверяется, что каждый вопрос в рейтинге самых сложных удовлетворяет:

```text
attempts >= MIN_ATTEMPTS
```

то есть вопросы с маленькой выборкой не попадают в основной рейтинг.

---

# 11. Важные ограничения интерпретации

## `difficulty` не является абсолютной сложностью вопроса

Низкая `accuracy` может зависеть не только от содержания вопроса, но и от:

- состава пользователей, которым он показывается;
- стадии обучения;
- предыдущей истории ошибок;
- `part` и тематики;
- положения вопроса в bundle;
- контекста предыдущих заданий.

Поэтому `difficulty` лучше интерпретировать как **наблюдаемую сложность в имеющемся пользовательском трафике**.

---

## `accuracy_gap` не доказывает эффект обучения

Если `experienced_accuracy > beginner_accuracy`, это не означает автоматически, что пользователи научились решать конкретный вопрос именно благодаря платформе.

Возможные альтернативные объяснения:

- до поздней стадии доходят более сильные пользователи;
- меняется состав пользователей;
- один и тот же вопрос может попадаться сегментам в разном контексте;
- объём наблюдений в beginner и experienced группах может сильно различаться.

Поэтому сравнение следует использовать как диагностический сигнал, а не как causal effect обучения.

---

## Время относится к bundle

`median_elapsed_time`, `mean_elapsed_time`, `fast_incorrect_rate` и `slow_incorrect_rate` используют восстановленное время question bundle.

Это значительно корректнее прямого использования `prior_question_elapsed_time`, но всё равно не позволяет измерить точное время конкретного вопроса внутри multi-question bundle.

---

## Дополнительные признаки не заменяют `difficulty`

`fast_incorrect_rate`, `slow_incorrect_rate` и `error_streak_before_avg` предназначены для дополнительной диагностики.

Основная метрика сложности остаётся:

```text
difficulty = 1 - accuracy
```

при условии достаточного числа наблюдений.
